# AFTERIMAGE Limited Drop

한정판 포스터 세 장을 판매하는 로컬 데모입니다. 브라우저에서 상품과 남은 수량을 보고 한 장씩 주문할 수 있습니다. 최근 확정 주문 세 건을 표시합니다.

## 실행

DBMS 저장소 루트에서 실행하세요. C 서버에는 Linux·macOS 또는 WSL이 필요하고, 웹 서버에는 Node.js 20 이상이 필요합니다. 형제 폴더 `SW-AI-W11-12-REACT`에서 Mini React 엔진 모듈을 직접 제공합니다.

터미널 1의 WSL Bash 또는 macOS·Linux 셸에서 아래 블록을 실행합니다.

```sh
make -C reliable &&
demo_dir=$(mktemp -d) &&
cp examples/limited-drop/data/drops.schema examples/limited-drop/data/drops.csv \
   examples/limited-drop/data/orders.schema examples/limited-drop/data/orders.csv "$demo_dir/" &&
echo "$demo_dir" &&
MINIDB_TOKEN=limited-drop-demo ./reliable/build/mini-db-server --data-dir "$demo_dir" --port 8080 --threads 4
```

터미널 2에서 웹 서버를 시작합니다. Windows에서 Node.js를 쓴다면 PowerShell 명령을 사용하세요.

```sh
MINIDB_TOKEN=limited-drop-demo node examples/limited-drop/server.mjs
```

```powershell
$env:MINIDB_TOKEN = 'limited-drop-demo'
$env:DROP_PORT = '13000'
node examples/limited-drop/server.mjs
```

브라우저에서 [상품 페이지](http://127.0.0.1:13000/)를 엽니다. `EACCES` 또는 `EADDRINUSE`가 나오면 `DROP_PORT`를 다른 포트(예: `13001`)로 지정해 다시 실행하고, 터미널에 표시된 주소를 엽니다. DBMS 주소는 `MINIDB_URL`로 바꿀 수 있습니다.

재시작 후 확인할 때는 앞서 출력된 데이터 경로로 DBMS만 다시 시작하고 화면의 **재고 및 주문 다시 조회**를 누르세요.

## 엔진을 어떻게 사용했는가

- 한 세션에서 재고를 조회하고 재고 차감과 주문 추가를 준비한 뒤 커밋합니다. 같은 시작 버전의 쓰기가 겹치면 먼저 확정한 쪽의 변경이 유지됩니다. 뒤 요청이 최신 버전에서 시작했다면 재고 0을 읽고 품절로 끝납니다.
- 재고는 기본 키 `id = 1`로 조회해 DBMS의 B+ 트리 경로를 사용합니다. 재고와 최근 주문은 같은 읽기 세션에서 조회해 화면에 함께 반영합니다.
- Mini React가 재고 텍스트, 주문 버튼, 상태 문구, 주문 목록을 갱신합니다. 목록의 `key`는 DBMS가 문자열로 돌려주는 주문 ID입니다. 엔진은 상태를 갱신할 때 새 Virtual DOM을 계산하고, diff 결과만 실제 DOM에 적용합니다.
- Node 웹 서버는 정적 파일 제공과 두 개의 업무 API를 담당합니다. DB 토큰과 SQL은 서버에 둡니다. 데모의 상품은 한 종류이며 두 서버는 로컬에서 실행합니다.

## 한계

- DBMS의 UPDATE는 리터럴 대입을 지원합니다. 웹 서버는 같은 트랜잭션에서 재고를 읽고 `BigInt`로 차감량을 계산합니다. 엔진은 변경된 재고 슬롯을 갱신하고 새 주문 슬롯을 추가합니다.

### 주문에서 드러나는 네 가지 한계

| 상황 | 재현 조건과 현재 동작 | 개선 방향 |
| --- | --- | --- |
| 같은 상품에 재고가 남아도 동시 주문 충돌 | 재고가 2장일 때 두 세션이 같은 재고 행을 읽고 차감과 주문 추가를 준비하면 첫 커밋은 확정되고 두 번째는 `ERR_CONFLICT`를 받습니다. 재고는 1장 남습니다. | 앱에서 미확정이 확인된 주문만 새 트랜잭션으로 제한적으로 재시도할 수 있습니다. |
| 응답이 끊겨 주문 결과를 모름 | 커밋 직후 응답이 유실되면 화면은 **결과 확인 필요**를 표시합니다. 주문 ID를 받은 경우 공용 이력에서 확인할 수 있습니다. 응답과 ID를 함께 잃으면 어떤 주문이 확정됐는지 특정하기 어렵습니다. | 앱에서 주문 전에 요청 ID를 만들고 주문과 함께 커밋합니다. 같은 ID로 다시 요청하면 기존 주문 결과를 반환할 수 있습니다. |
| 한 고객이 여러 장 구매 | 재고가 남아 있을 때 같은 고객이 주문을 반복하면 주문마다 새 기록이 생깁니다. 현재 주문에는 고객 식별자가 없습니다. | 앱에서 고객을 식별하고 구매 한도 확인과 주문 생성을 한 트랜잭션으로 묶습니다. |
| 새 기기에서 내 주문을 찾기 어려움 | 다른 브라우저에서 페이지를 열면 최근 확정 주문의 공용 목록이 표시됩니다. 본인 주문만 확인할 수 있는 정보가 없습니다. | 앱에서 주문을 고객 계정에 연결하거나 주문 확인 링크를 발급합니다. |

표의 개선 방향은 후속 설계입니다. 결제는 데모 범위 밖입니다.

### 해결한 엔진 한계

이전에는 두 트랜잭션이 서로 다른 재고 행을 변경해도 먼저 커밋한 쪽이 DB 전체 버전을 바꾸면 나머지가 충돌했습니다. 이제 기본 키로 접근한 행의 버전이 모두 그대로라면 변경분을 최신 상태에 합쳐 두 트랜잭션을 각각 확정할 수 있습니다. 같은 행을 읽거나 수정한 경우에는 그 행이 바뀌면 충돌합니다. 범위 조회와 전체 스캔에는 기존 전역 검사를 적용합니다.

재현과 검증은 [엔진 테스트](../../reliable/tests/test_engine.c)에서 수행합니다. 두 세션의 겹치는 트랜잭션으로 독립 행의 변경과 같은 행의 충돌을 비교합니다.

WSL2에서 변경 전 커밋 `6d5280b`와 개선 엔진을 비교했습니다. 두 세션이 같은 버전에서 시작해 서로 다른 재고 행을 갱신하고 각각 주문을 추가하는 작업을 실행했습니다. 두 세션이 모두 변경을 준비한 뒤 차례로 커밋했습니다. 매번 새 임시 DB에서 2,000쌍씩 5회 실행했고, HTTP를 거치지 않고 엔진 API에서 SQL을 실행했습니다.

| 지표 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 첫 시도 확정 | 2,000 / 4,000 | 4,000 / 4,000 |
| 충돌 | 2,000 | 0 |
| 전체 실행 시간 중앙값 | 44.31 ms | 74.58 ms |
| 초당 확정 커밋 수 중앙값 | 45,137 | 53,633 |

두 번째 커밋을 WAL 버퍼를 파일로 내보내기 직전, 커밋 WAL 동기화 직후, 바이너리 슬롯 부분 반영 중에 각각 외부에서 `SIGKILL`했습니다. 첫 경우에는 첫 번째 주문과 재고 변경만 복구됐고, 나머지 두 경우에는 두 주문과 재고 변경이 모두 복구됐습니다. 각 DB를 두 번 다시 열어 동일한 결과를 확인했습니다.

## 검증

새 데모 DB를 띄운 뒤 같은 접속 환경에서 `node examples/limited-drop/verify.mjs`를 실행하면 HTML과 엔진 모듈 제공, 두 건의 확정 주문, 마지막 한 장의 동시 주문, 최종 품절 상태를 실제 HTTP로 검사합니다. 이 검사는 데모 재고 세 장을 모두 사용합니다.
