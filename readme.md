# MINI DBMS

## 개요

C로 구현한 학습용 DBMS입니다.

SQL 처리, 데이터 저장과 조회, 인덱스, 트랜잭션 및 장애 복구를 구현하며 데이터베이스의 내부 동작을 이해하는 것을 목표로 합니다.

## 설계 목표

파일을 직접 읽고 쓰는 것으로도 데이터를 저장하고 조회할 수 있습니다.

그렇다면 파일시스템이 아닌 DBMS를 사용하는 이유가 명확해야합니다.

 - MINI DBMS는 애플리케이션이 데이터의 일관성과 저장 결과를 신뢰할 수 있어야 합니다.
 - 개발자는 각종 장애가 발생하는 케이스를 고민하지 않아도 되어야 합니다.

따라서 DBMS의 내부 동작을 직접 구현하면서, 작업 도중 프로그램이 종료되더라도 데이터의 일관성을 유지하고, 저장에 성공한 데이터는 장애 이후에도 보존되도록 하는 것을 주요 목표로 삼았습니다.

## 특징

### 1. WAL 기반 커밋

- WAL(Write-Ahead Logging)은 데이터 파일을 변경하기 전에 변경 내용을 로그에 먼저 기록하는 방식입니다.
- 장애 발생 후 로그를 이용해 완료되지 않은 트랜잭션의 변경을 복구합니다.

#### 도입 이유

- 여러 테이블을 순서대로 변경하다 프로세스가 종료되면, 일부 테이블에만 변경이 반영될 수 있습니다.
- 이때 데이터 파일만으로는 작업 전체가 커밋됐는지 판단하기 어렵습니다.
- 따라서 변경 내용과 커밋 여부를 별도 로그에 남겨, 데이터 파일의 반영 상태와 관계없이 복구할 수 있도록 했습니다.

#### 적용 방식

- 변경 내용과 COMMIT 기록을 WAL에 순서대로 기록합니다.
- WAL 버퍼를 flush하고 fsync를 완료한 뒤 데이터 파일에 변경을 반영합니다.
- 재시작 시 초기 데이터를 불러온 뒤, WAL에서 COMMIT이 확인된 트랜잭션만 기록된 순서대로 재적용하여 복구합니다.

### 2. 스냅샷

- 스냅샷은 특정 시점의 데이터 상태를 보존하여, 이후 데이터가 변경되더라도 당시의 상태를 조회할 수 있도록 하는 구조입니다.
- 트랜잭션마다 읽을 데이터 버전을 고정하고, 변경된 부분에 대해서만 새 버전을 생성하여 데이터 전체를 복사하는 비용을 줄였습니다.

#### 도입 이유

- 데이터를 직접 덮어쓰면, 여러 데이터를 순차적으로 조회하는 도중 다른 트랜잭션이 커밋했을 때 변경 전후의 값이 섞일 수 있습니다.
- 이를 방지하기 위해 조회하는 동안 변경을 차단할 수도 있지만, 긴 조회 작업이 다른 트랜잭션의 쓰기를 지연시키게 됩니다.
- 따라서 기존 데이터의 버전을 보존하여 조회와 변경이 서로 다른 데이터 상태를 사용할 수 있도록 했습니다.

#### 적용 방식

- 트랜잭션이 시작할 때 현재 커밋된 데이터 상태를 참조합니다.
- 변경 시 새 버전 생성: 기존 데이터를 덮어쓰지 않고 변경된 부분에 새로운 버전을 생성합니다.
- 기존 트랜잭션은 변경 전 데이터를 계속 읽고, 새로 시작한 트랜잭션은 변경이 반영된 데이터를 읽습니다.
- 트랜잭션 내부에서 변경한 데이터는 자신의 조회에 반영하되, 커밋 전까지 다른 트랜잭션에는 노출하지 않습니다.
- 이전 버전을 참조하는 트랜잭션이 모두 종료된 후 해당 버전을 정리합니다.

### 3. 트랜잭션

- 트랜잭션은 여러 SQL 작업을 하나의 단위로 묶어, 모든 변경을 커밋하거나 취소할 수 있도록 하는 기능입니다.
- `BEGIN`, `COMMIT`, `ROLLBACK`을 통해 작업의 시작과 종료를 관리하고, 커밋되지 않은 변경이 다른 트랜잭션에 노출되지 않도록 했습니다.

#### 도입 이유

- 여러 테이블을 변경하는 작업에서 일부 SQL만 성공하면 데이터 간 일관성이 깨질 수 있습니다.
- 각 SQL을 개별적으로 확정하면 중간에 오류가 발생했을 때 애플리케이션이 이전 변경을 직접 되돌려야 합니다.
- 따라서 여러 SQL을 하나의 트랜잭션으로 묶고, 작업 전체를 성공시키거나 취소할 수 있도록 했습니다.

#### 적용 방식

- BEGIN: 트랜잭션을 시작하고, 이후 실행되는 SQL의 변경을 하나의 작업으로 관리합니다.
- COMMIT: 트랜잭션의 변경을 WAL에 기록하고 `fsync`를 완료한 뒤 작업의 성공을 확정합니다.
- ROLLBACK: 커밋되지 않은 변경을 폐기하여 트랜잭션 시작 이전의 데이터 상태를 유지합니다.

## 성능 최적화

### 1. 고정 길이 바이너리 슬롯

- 기존 CSV 방식에서는 한 행의 수정·삭제에도 전체 파일을 재작성하고 인덱스를 재구축해야 했습니다.
- 이를 개선하기 위해 고정 길이 바이너리 슬롯을 도입하여, 레코드의 저장 위치를 유지하고 해당 슬롯만 수정할 수 있도록 했습니다.
- 결과적으로 불필요한 파일 I/O와 인덱스 재구축 비용을 줄였습니다.

### 2. WAL 버퍼링

- 삽입 과정의 소요 시간을 계측한 결과, 작은 WAL 쓰기 요청이 반복되는 것이 병목임을 확인했습니다.
- WAL 기록을 64KiB 버퍼에 모아 처리하여 쓰기 호출 횟수를 줄였습니다.
- 커밋 성공 전 `flush`와 `fsync`를 완료하는 조건은 유지하여 영속성 보장을 변경하지 않았습니다.
