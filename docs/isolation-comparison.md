# 스냅샷 조회와 2PL 조회 비교

현재 엔진에서는 일반 조회를 스냅샷으로 유지하는 편이 이번 작업 부하에서 유리했습니다. 한 스레드의 짧은 조회 차이는 작았고, 8개 스레드에서는 조회 잠금의 비용이 늘었습니다. 같은 행의 읽기 트랜잭션이 길어지면 2PL의 쓰기는 읽기가 끝날 때까지 기다렸습니다.

## 비교 대상

- **Snapshot**: 현재 `e69bdf2` 엔진. 일반 SELECT는 BEGIN 스냅샷을 읽고, 수정과 FOR UPDATE는 배타 잠금을 사용합니다.
- **2PL**: 같은 엔진의 비교용 빌드. 일반 SELECT는 공유 잠금을, 수정과 FOR UPDATE는 배타 잠금을 잡고 트랜잭션 종료까지 유지합니다. 일반 조회도 잠금 확보 후 최신 커밋 데이터를 읽습니다. 공유 잠금끼리는 공존합니다.
- **2PL + 쓰기 우선**: 대기 중인 쓰기가 있으면 같은 대상의 새 공유 잠금이 먼저 들어오지 않도록 한 비교용 빌드입니다. 잠금 대기 순서가 결과에 주는 영향을 구분하기 위해 추가했습니다. FIFO를 구현한 것은 아닙니다.

프로덕션 엔진은 변경하지 않았습니다. Python 드라이버가 비교용 엔진 소스를 `reliable/build/isolation-compare/`에 생성하고 별도로 컴파일합니다. **두 2PL 빌드에도 기존 COW·스냅샷 저장 구조는 남아 있습니다.** 따라서 독립적으로 최적화한 순수 2PL 엔진과 MVCC 엔진의 일반적인 우열을 증명하는 실험이 아닙니다. 같은 엔진에서 조회 잠금 정책을 바꾼 비용을 비교합니다.

스냅샷 조회와 2PL의 격리 의미도 동일하지 않습니다. 현재 방식은 일반 조회의 의존성을 잠금으로 보호하지 않으므로 조회 후 계산해서 수정하는 업무에는 FOR UPDATE가 필요합니다. 성능만으로 모든 조회를 스냅샷으로 처리해도 된다는 결론을 내릴 수는 없습니다.

## 조건

- Apple M2 / macOS 26.5.1 ARM64 / Apple clang 21.0.0, C11 `-O2`.
- HTTP를 제외하고 `mdb_execute()` 엔진 API를 호출했습니다. WAL 기록·fsync·바이너리 저장·COW는 같은 구현입니다.
- 각 모드·반복마다 새 임시 DB를 만들었습니다. 1,000행, `id INT AUTO`, `value INT`, 초기 값은 모두 0입니다.
- 시작 전 기본 키 조회 1,000회로 워밍업했습니다. 모드별 3회 실행하고 반복마다 모드 순서를 뒤집었습니다.
- 각 실행의 분위수는 최근접 순위입니다. 아래 표의 각 수치는 실행 3회의 해당 통계 중앙값입니다. 서로 다른 통계의 중앙값이 반드시 같은 실행에서 나온 것은 아닙니다.
- 짧은 기본 키 조회: 총 80,000회, 동시 1/8 스레드. 각 SELECT는 자동 커밋입니다.
- 혼합 부하: 동시 8스레드(읽기 7, 쓰기 1), 각 1.5초. 읽기는 BEGIN → SELECT → **0.5ms 대기 요청** → COMMIT으로 처리 시간을 흉내 냈습니다. 쓰기는 자동 커밋 UPDATE입니다. 읽기 지연은 이 전체 읽기 트랜잭션을 포함합니다.
- 독립 행 혼합 부하는 읽기 대상과 쓰기 대상을 분리했습니다. 같은 행 혼합 부하는 모두 id=1을 다룹니다. 시간 기반 부하이므로 완료 요청 수는 결과이며 모드 간 같지 않습니다.
- 긴 읽기: 일반 조회 후 **10ms 대기 요청**을 넣었습니다. 실제 타이머 지연과 스케줄링 때문에 읽기는 대략 12~13ms 유지됐습니다. 실행당 30회. 엔진의 잠금 대기 후크/쓰기 완료 이벤트를 관측한 뒤 읽기를 종료하므로 겹침을 단순 sleep으로 가정하지 않았습니다.

## 조회만 수행

총 80,000회 완료 시간입니다. 모든 요청이 성공했습니다.

| 동시 스레드 | Snapshot | 2PL | 2PL + 쓰기 우선 |
|---:|---:|---:|---:|
| 1 | 105.363ms | 117.454ms | 107.854ms |
| 8 | 163.422ms | 215.537ms | 210.348ms |

8스레드에서 쓰기 우선 2PL은 스냅샷 대비 전체 시간이 약 28.7% 더 걸렸습니다. 한 스레드에서는 쓰기 우선 2PL과의 차이가 약 2.4%로 작았습니다. 마이크로초 단위 개별 요청 시간보다 80,000회 전체 시간을 중심으로 해석했습니다. 8스레드 개별 조회 p95는 각각 0.050ms / 0.066ms / 0.065ms였습니다.

## 읽기·쓰기 혼합

각 약 1.5초 동안 완료한 작업 수와 성공한 쓰기 지연입니다. 쓰기 한 건에는 WAL 동기화와 커밋이 포함됩니다.

| 조건 | 방식 | 읽기 완료 | 쓰기 완료 | 쓰기 p50 | 쓰기 p95 |
|---|---|---:|---:|---:|---:|
| 독립 행 | Snapshot | 12,005 | 19,943 | 0.074ms | 0.090ms |
| 독립 행 | 2PL | 11,379 | 19,982 | 0.073ms | 0.091ms |
| 독립 행 | 2PL + 쓰기 우선 | 11,527 | 19,632 | 0.074ms | 0.090ms |
| 같은 행 | Snapshot | 11,253 | 18,103 | 0.079ms | 0.092ms |
| 같은 행 | 2PL | 15,151 | 7 | 3.520ms | 897.168ms |
| 같은 행 | 2PL + 쓰기 우선 | 4,207 | 1,504 | 1.007ms | 1.276ms |

독립 행의 쓰기 처리에서는 큰 차이를 관측하지 못했습니다. 같은 행에서는 새 공유 잠금이 계속 들어오는 단순 2PL의 쓰기가 밀렸습니다. 반복별 쓰기 완료는 7/3/19건뿐이므로 이 경우의 지연 분위수는 표본이 적습니다. 읽기 완료가 늘어난 것 역시 쓰기가 거의 진행되지 않은 상태의 결과입니다.

쓰기 우선 처리를 추가하면 쓰기도 꾸준히 진행됐지만, 읽기와 쓰기가 서로 기다리는 비용은 남았습니다. 같은 행 읽기 p95는 스냅샷 1.267ms, 쓰기 우선 2PL 5.985ms였습니다. 이 조건의 0.5ms 읽기 대기는 의도적으로 넣은 값이며 일반 GET의 기본 지연이 아닙니다.

## 긴 읽기와 겹친 쓰기

| 방식 | 성공한 쓰기 p50 | 성공한 쓰기 p95 |
|---|---:|---:|
| Snapshot | 0.242ms | 0.608ms |
| 2PL | 13.162ms | 13.411ms |
| 2PL + 쓰기 우선 | 13.084ms | 13.356ms |

스냅샷에서는 읽기가 예전 값을 유지하는 동안 쓰기가 완료됐습니다. 2PL에서는 공유 잠금이 풀린 다음 쓰기가 완료됐습니다. 이것은 의도한 동시성 제어 방식의 차이이며, 쓰기 자체가 10ms의 CPU 작업을 더 수행한 결과가 아닙니다.

최종 측정의 9개 실행 × 5개 조건에서 오류와 잠금 타임아웃은 모두 0이었습니다. 공유 잠금의 공존 검사와 긴 읽기의 270회 겹침 검사에서 2PL 쓰기의 실제 대기, 스냅샷 쓰기의 선행 완료, 기존 읽기 값 유지와 새 조회의 변경 값 확인을 통과했습니다. 비교용 2PL 전체에 대한 별도의 장애·교착·직렬화 가능성 검증을 완료했다는 뜻은 아닙니다.

`--output`으로 결과 경로를 바꿀 수 있습니다. 원본에는 각 반복의 완료 수·오류 수·지연·처리량, 기준 커밋과 엔진 SHA-256을 기록합니다. 작업이 없는 종류의 지연은 JSON에서 0으로 표시하며 성능 값으로 해석하지 않습니다.

이번 결과는 현재 선택한 **일반 스냅샷 조회 + 필요한 행의 명시적 잠금**을 유지할 근거가 됩니다. 일반 조회 전체에 잠금을 적용하려면 격리 수준에서 얻는 이점과 함께 읽기 트랜잭션 길이, 경합률, 대기 순서 정책도 판단해야 합니다. HTTP 성능, WSL/Linux 결과, 대규모 데이터·장기 실행·메모리 사용량 비교는 이번 측정에 포함하지 않았습니다.
